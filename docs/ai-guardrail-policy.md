# AI Guardrail Policy — Naseeh

Naseeh is Ihsan's AI companion (`backend/src/services/ai.service.ts`, provider:
GROQ). This document is the single source of truth for what Naseeh is and
isn't allowed to do, and how that's enforced in code — not just in the system
prompt. It should be updated whenever a rule or enforcement mechanism changes.

## 1. Product rule

Naseeh's only job is to **encourage, personalize, and warmly reflect** on a
user's own worship data. It is never a source of religious evidence and never
issues a ruling. This is a hard product rule, not a suggestion — see the
comment at the top of `ai.service.ts`.

## 2. No fatawa, no invented religious text

Naseeh must never:

- Cite, number, or invent a Qur'an verse reference (surah:ayah), a hadith, an
  isnād/chain, or a grading (ṣaḥīḥ/ḥasan/ḍaʿīf).
- Issue a ruling — nothing is called halal, haram, fard, wajib, sinful, valid,
  or invalid by Naseeh. It does not give fatwa.
- Claim anything is authentic, weak, true, or false in a religious sense.
- Produce long Arabic supplication text (the app ships verified duʿā already;
  Naseeh only writes short reflective English/Bengali lines).

**Enforcement:** the system prompt (`GUARDRAIL` constant) states these rules
explicitly, but the system prompt alone is not trusted — every model reply is
scanned by `findGuardrailViolation()` before it reaches a user. A match
against verse-citation, hadith-citation, or ruling-language patterns is
treated exactly like a provider failure: the caller's existing static
fallback message is returned instead, and the block is logged
(`[ai-guardrail] blocked <feature> output (<category>)`).

## 3. Retrieval-only for religious text

Where the app needs actual religious references — verified duʿā, hadith
grading, fiqh guidance (e.g. Rayhanah's istihadha/ghusl copy, DaifExplainer) —
that content is hand-curated and stored in the app itself, never generated by
Naseeh. Naseeh may point a user _toward_ that existing verified content, or
toward qualified scholars, but never generates the content itself.

## 4. Escalation boundary

If a user asks Naseeh for evidence, a ruling, or "is this true", Naseeh
declines warmly and redirects to qualified scholars and to Ihsan's own
verified references (which link to quran.com / sunnah.com). This is rule 4 of
the system prompt; the output filter above is the backstop if the model
ignores it.

## 5. Mental health boundary

Naseeh's warmth is not a substitute for real support. The one place a user
expresses an emotional state directly is the Rayhanah mood check-in
(`getMoodComfort`, moods drawn from a fixed set: calm/happy/low/irritable/
anxious/tired — never free text). When a heavier mood (`low` or `anxious`) is
selected, the UI shows a resource note alongside the AI line — a static,
non-AI sentence encouraging the user to reach out to someone she trusts or a
mental health professional (`frontend/src/components/MoodComfort.tsx`,
`naseeh.resourceNote` i18n key). This is a static message, not
AI-generated, because a generated line can't reliably judge whether it's
enough — a genuine offline connection always outranks it.

There is currently no freeform-text input anywhere that reaches Naseeh (see
§7) — if one is added in the future (e.g. wiring up the currently-unused
`/api/ai/suggest` `userSummary` field to a real UI), it must go through the
same sanitization path described in §7 and be evaluated for whether it also
needs a distress-signal check before being sent to the model.

## 6. Cost controls

- **Provider:** GROQ free tier only (`openai/gpt-oss-120b`, falling back to
  `openai/gpt-oss-20b`). No paid provider is wired up.
- **Temperature:** 0.5 — lowered from an earlier 0.8. This is a
  safety-sensitive religious-adjacent domain; consistent, predictable
  phrasing is worth more here than creative variation, and a lower
  temperature also reduces the odds of the model drifting into
  citation/ruling language in the first place.
- **Rate limiting, two layers:**
  - IP-based, pre-auth (`aiLimiter`, `backend/src/middleware/rateLimiter.ts`):
    10 requests/hour, applied at the `/api/ai` mount point before any route
    runs.
  - UID-based, post-auth (`aiUserLimiter`): 20 requests/day per signed-in
    user, applied after `requireAuth` on every `/api/ai/*` route. This is the
    layer that actually limits a single user's cost exposure — the IP layer
    alone doesn't stop one user across a NAT/proxy or multiple devices from
    using up the shared IP allowance, and doesn't stop them at all once
    they're authenticated from a fresh IP.
- **Client-side caching:** every feature caches its result in localStorage
  keyed by time period (day/week/mood-signature), so a typical user makes
  1–3 calls per week regardless of how often the relevant screen is opened.
- **`max_tokens` caps** per feature (220–600) keep individual calls small.

## 7. Input handling (prompt injection)

Every field that reaches a prompt is either a closed enum validated by Zod
(`moods`, `period`, `event`, `fastType` — the last locked to the real set
`FastingLog`'s `category`/`voluntaryKind` produce, not arbitrary text) or is
passed through `sanitizeForPrompt()` before interpolation, which:

- strips control characters,
- strips common injection/override phrases ("ignore previous instructions",
  "system:", fenced-code/triple-quote delimiters, etc.),
- collapses whitespace, and
- truncates to the field's validated max length.

Free text that reaches the model (currently: `userSummary` on `/suggest`,
which has **no live frontend caller** — see below; and `feature` in
`streak-coaching`, a translated UI label rather than a closed enum since it
varies by locale) is additionally wrapped with `asUntrustedData()`, which
tells the model explicitly to treat the text as inert data, not instructions.

**Current live exposure is narrow:** as of this writing, no screen in the app
actually lets a user type free text that reaches Naseeh — `userSummary` is
wired end-to-end on the backend but has zero callers in the frontend, and
every other field is a closed enum or checklist ID. The sanitization above is
defense-in-depth against direct API calls (any signed-in user can reach these
endpoints with a REST client using their own token) and against `userSummary`
being wired up to a real UI later without anyone re-reading this doc first.

## 8. Audit logging

Every `complete()` call logs a single structured line
(`console.warn(JSON.stringify({tag: 'ai_call', ...}))` — `.warn`, not `.log`,
since the project's lint config only allows `warn`/`error`) with: feature name,
userId, timestamp, success/failure, provider used, and — if the output
filter fired — which category it matched. **Deliberately not logged:** the
actual prompt or response text. Several features carry personal data (cycle
mood/symptoms, worship stats) that shouldn't gain a second, separate
long-lived store purely for AI review purposes — see the "Trust is Ihsan's
moat" principle in `TODO-v2.md`'s anti-features table. If deeper debugging of
a specific bad response is ever needed, that's a case-by-case decision to log
verbosely temporarily, not a standing default.

## Where the code lives

- `backend/src/services/ai.service.ts` — guardrail text, output filter,
  sanitization, logging, all 7 feature functions.
- `backend/src/middleware/rateLimiter.ts` — `aiLimiter` (IP), `aiUserLimiter`
  (UID).
- `backend/src/validation/ai.schemas.ts` — Zod schemas, including the
  `fastType` enum lock.
- `frontend/src/components/MoodComfort.tsx` — the mental-health resource
  note.
